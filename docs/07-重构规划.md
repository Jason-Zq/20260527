# 07 · 重构规划

> 目标架构：**Python 纯 OCR 微服务 + .NET Web 业务系统 + 保留 PostgreSQL**。前端本轮不动。

## 1. 目标架构总览

```text
┌────────────────────────┐
│ 前端 Vue 3（不动）      │
└───────────┬────────────┘
            │ HTTP /api/*（契约保持不变）
┌───────────▼─────────────────────────────────────────┐
│ .NET Web 业务系统（ASP.NET Core Web API）            │
│  ├─ Controllers        复刻 72 个 API 契约            │
│  ├─ Services           业务编排（留底检测/解析/模板…） │
│  ├─ LLM Client         OpenAI 兼容调用 + prompt 模板   │
│  ├─ BackgroundService  worker（抢任务）+ finalize + watchdog + GC │
│  ├─ EF Core / Npgsql   PostgreSQL 访问                │
│  └─ OcrClient          HTTP 调用 Python OCR 微服务     │
└───────┬────────────────────────────┬─────────────────┘
        │ EF Core                     │ HTTP
┌───────▼────────┐          ┌─────────▼──────────────────┐
│ PostgreSQL     │          │ Python OCR 微服务（FastAPI） │
│（保留，表不变） │          │  ├─ /ocr/extract 多格式抽取  │
└────────────────┘          │  ├─ /ocr/image  单图+坐标    │
                            │  ├─ /ocr/pdf-pages 全页 OCR │
                            │  ├─ 下载 + URL 刷新          │
                            │  └─ RapidOCR / pdfplumber…  │
                            └─────────────────────────────┘
                                    │ HTTP
                            业务方文件服务 getFileDownloadUrl
```

## 2. 边界划分（关键决策：纯 OCR 微服务）

### 2.1 保留在 Python OCR 微服务
| 能力 | 现有实现 | 说明 |
|------|---------|------|
| 多格式文本抽取 | `text_extractor.extract_text` | .pdf/.doc/.docx/.xls/.xlsx/.pptx/图片/.gif |
| 单图 OCR（含 bbox） | `ocr_service.run_ocr`/`extract_image_file` | 证件解析定位用 |
| PDF 全页 OCR | `split_ocr_service.split_extract_all_pages` | PDF 拆分用 |
| PDF 类型判断 | `ocr_service.detect_pdf_type` | 文字型/图片型 |
| 文件下载 + URL 刷新 | `file_fetcher` | 含业务方 getFileDownloadUrl 身份参数刷新 |
| 临时文件清理 | `file_fetcher.periodic_cleanup_task` | Windows WinError 32 处理（Linux 无此问题可简化） |
| NUL/控制字符清洗 | `text_extractor._sanitize_text` | 抽取出口清洗 |

### 2.2 迁到 .NET
| 能力 | 现有实现 | .NET 对应 |
|------|---------|----------|
| 全部 HTTP API（72 个） | `main.py` | Controllers |
| 留底检测编排 | `archive_detect_service.py` | Services |
| worker 队列（抢任务/处理/写终态） | `worker_runner.py` | `BackgroundService` + Npgsql SKIP LOCKED |
| finalize 轮询 / watchdog / GC | `main.py` 后台协程 | `BackgroundService` |
| LLM 调用 + 所有 prompt + 分类体系 + PSD 口径 | `llm_service.py` | LLM Client + prompt 常量 |
| 脱敏 | `redactor.py` | C# 正则重写（见 §2.3） |
| DB 访问 + 状态机 | `db/*_crud.py` | EF Core / Npgsql |
| 客户档案生成 / 模板 / 拆分编排 / 摘要 | 各 service | Services |
| 请求日志中间件 | `request_log_middleware.py` | ASP.NET Core Middleware |

### 2.3 需要处理的两个"跨界"依赖
1. **大文件采样初判 `detect_large_table_doc`**（现在 OCR 抽取内部调 LLM）：
   - **方案 A（推荐）**：OCR 微服务 `/ocr/extract` 增加参数 `sample_strategy`（`none`/`head_tail`/`head_only`）+ `early_exit_threshold`，由 .NET 决定是否采样。OCR 微服务不再依赖 LLM。
   - 方案 B：OCR 微服务先 OCR 前 2 页返回给 .NET，.NET 调 LLM 判定后再回调 OCR 微服务要采样结果（两次往返，不推荐）。
2. **脱敏 `redactor`**：
   - **方案 A（推荐）**：迁到 .NET（纯正则，C# 等价重写），OCR 微服务只返回原文。.NET 在写 DB 前脱敏 `ocr_text`/`reason`/`key_points`。
   - 方案 B：OCR 微服务 `/ocr/extract` 加 `redact=true` 开关返回已脱敏文本。但脱敏也用于 LLM 输出（reason/key_points），那部分必须在 .NET，所以脱敏逻辑无论如何要在 .NET 有一份——**建议统一放 .NET**。

## 3. OCR 微服务 API 设计（建议）

```text
POST /ocr/extract
  请求: { "url": "...", 或 multipart file, "mime_type": "...",
          "sample_strategy": "none|head_tail|head_only",
          "early_exit_threshold": 10 }
  响应: { "text": "...", "source": "pdf_text|pdf_ocr|pdf_ocr_sampled|docx_text|...",
          "page_count": int, "char_count": int }

POST /ocr/image        # 单图 OCR，返回含坐标（证件解析定位）
  响应: { "pages": [{ "page":1, "text":"...", "ocr_details":[{text,confidence,bbox}] }] }

POST /ocr/pdf-pages    # PDF 全页 OCR（拆分用，返回每页文本）
  响应: { "total_pages": int, "pages": [{page, text}] }

POST /files/refresh-url  # （可选）URL 刷新，若下载留在 OCR 微服务侧
  请求: { "file_id": "...", "type": "preview" }
  响应: { "url": "...", "expires_at": "..." }

GET /healthz            # OCR 引擎就绪 + 依赖检查
```

**是否让 OCR 微服务承担下载**：两种都可行。
- 若 OCR 微服务承担下载（传 URL）：业务方文件服务耦合留在 Python，.NET 只管 file_id/url 透传。
- 若 .NET 承担下载（传文件流）：OCR 微服务更纯，但大文件走两跳（业务方→.NET→OCR）。
- **建议 OCR 微服务接受 URL 直接下载**（少一跳，且下载+URL刷新逻辑已成熟），.NET 传 URL + file_id。

## 4. 迁移步骤（分阶段，可灰度）

### 阶段 0：准备
1. 用本 docs 目录作为 .NET 复刻的规格书。
2. `dotnet ef dbcontext scaffold` 从现有 PostgreSQL 反向生成 EF Core 模型（或 Code-First 按 [03](03-数据库设计.md) 手写）。**先跑 `alembic upgrade head` 确保 schema 完整，核对 `api_request_logs.source` 列**（见 [03 §7.2](03-数据库设计.md) 漂移警告）。
3. 抽取 Python OCR 微服务：从现 backend 剥离 `ocr_service`/`text_extractor`/`split_ocr_service`/`file_fetcher`，去掉 `detect_large_table_doc`（LLM）依赖，包一层 FastAPI HTTP。

### 阶段 1：OCR 微服务独立
1. Python OCR 微服务按 §3 暴露 API，独立部署（systemd 或容器）。
2. 现 FastAPI backend 改为 HTTP 调 OCR 微服务（先验证微服务契约，此时业务仍在 Python）。
3. 验收：留底检测/解析/拆分/摘要全流程仍正常。

### 阶段 2：.NET 业务系统
1. .NET Web API 复刻 72 个接口（优先主线：留底检测 business/batch + 轮询 + admin）。
2. .NET worker（`BackgroundService`）复刻队列状态机（Npgsql SKIP LOCKED），OCR 步骤调 Python 微服务，LLM/脱敏/finalize 在 .NET。
3. LLM prompt / 分类体系 / PSD 口径从 [05](05-业务服务与队列.md) 翻译成 C# 常量。
4. finalize 轮询 / watchdog / GC 用 `BackgroundService`。

### 阶段 3：切流与下线
1. nginx `/api/` 从 FastAPI(:8000) 切到 .NET(:5000)，OCR 微服务保持独立端口。
2. 灰度：可按接口逐个切（如先切只读的 admin 查询，再切 business/batch）。
3. 全部切完后下线 Python FastAPI backend，只留 OCR 微服务。

## 5. .NET 侧关键技术点

| 现有 Python 机制 | .NET 对应 |
|-----------------|----------|
| SQLAlchemy async + asyncpg | EF Core + Npgsql（原生 async） |
| `SELECT FOR UPDATE SKIP LOCKED` | `context.Database.ExecuteSqlRaw` 或 Dapper 原生 SQL |
| worker 独立进程 | `BackgroundService`（可多实例，或独立 worker 进程 + 同库抢任务） |
| 内存态 `_batch_status` 轮询缓存 | `IMemoryCache`（若单实例）或直接查 DB（.NET 多线程无 --workers=1 限制，可去掉内存缓存直接读 DB） |
| asyncio.create_task fire-and-forget | `Task.Run` / `Channel<T>` / 后台队列 |
| JSONB（extracted_fields/key_points/…） | Npgsql `jsonb` 映射（`JsonDocument` 或 POCO + `System.Text.Json`） |
| openai SDK | `OpenAI` NuGet 或 `HttpClient` 直调（OpenAI 兼容接口） |
| 30 天 GC 循环 | `BackgroundService` + `PeriodicTimer` |
| NUL 清洗（`_clean_text`） | C# `string` 过滤 C0 控制符（保留 `\t\n\r`），入库前统一清洗 |

> **可简化点**：.NET 天然多线程，不需要 Python 的 async/sync 双引擎，也不需要 `--workers=1` + 内存缓存 fast-path——可直接多实例读 DB。worker 是否独立进程可选：.NET 后台服务与 Web 同进程或独立均可，取决于是否要 OCR 崩溃隔离（现架构是隔离的，建议保留独立 worker 部署单元）。

## 6. 风险与注意事项

| 风险 | 说明 | 缓解 |
|------|------|------|
| LLM prompt 语义漂移 | prompt 是业务核心，翻译成 C# 常量时字面必须一致 | 逐字迁移 [05 §3.4/3.5](05-业务服务与队列.md)，保留中文原文；用相同输入对比 Python/新系统输出 |
| 脱敏规则遗漏 | 正则迁移易漏边界 case | 复用 `tests/test_redactor.py` 的断言在 .NET 重写一遍 |
| `api_request_logs.source` schema 漂移 | ORM 有列但迁移未建 | 建库前核对，补 add column |
| DB 状态机竞态 | SKIP LOCKED + lease 续租 + watchdog 三者配合 | .NET 严格复刻 lease 时长(600s)、MAX_RETRY_COUNT(1)、续租时机 |
| OCR 微服务串行瓶颈 | RapidOCR 引擎锁串行 | 微服务可多副本水平扩展（无状态），.NET 侧按 file_id 分发 |
| 增量复用逻辑 | `(progress_id, file_id)` 命中历史 done 复用 | 复刻 `find_latest_done_files_bulk` 的 DISTINCT ON 查询 |
| Word 渲染跨平台 | docx2pdf(Win) / soffice(Linux) | .NET 侧统一走 LibreOffice headless（生产 Linux），或调独立渲染服务 |

## 7. 验收标准

- [ ] 前端不改代码，指向新 .NET 后端后所有页面功能正常。
- [ ] 留底检测 business/batch 提交 → worker 处理 → overall 生成，全链路与旧系统结果一致（同输入对比 verdict/score）。
- [ ] 增量复用命中率与旧系统一致。
- [ ] OCR 微服务对多格式文件抽取结果与旧系统一致（text/page_count/char_count）。
- [ ] NUL 字节文件不再触发 PG `CharacterNotInRepertoireError`。
- [ ] LLM 调用/事件/请求/外部接口四类日志正常落库，30 天 GC 生效。
- [ ] 健康检查 `/healthz` 真实反映 DB + worker 状态。
- [ ] 部署：systemd/容器 + nginx 反代，OCR 微服务与 .NET 服务独立可重启。
