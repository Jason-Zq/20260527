# 05 · 业务服务与队列

> **这是重构后迁到 .NET 的部分。** 涵盖留底检测编排、worker 队列状态机、LLM prompt 与判定口径、其他流水线。
>
> 涉及文件：`archive_detect_service.py`、`worker_runner.py`、`llm_service.py`、`client_profile_service.py`、`template_service.py`、`split_service.py`、`event_service.py`、`middleware/request_log_middleware.py`。

## 1. 文件留底检测编排（`archive_detect_service.py`）

### 1.1 提交入队 `submit_business_batch(...)`
1. 校验 items（URL http/https、stage 合法）。
2. `upsert_client_by_code` upsert 客户、`upsert_progress` upsert 进展包。
3. **增量复用**：`find_latest_done_files_bulk(progress_id, file_ids)` 一次查同 progress 下各 file_id 最新 done 记录；命中则直接拷贝旧结果（`is_reused=true`, `elapsed_sec=0`），跳过 OCR/LLM。
4. `create_business_batch_with_files` 一次事务写 batch + N 个 file 行（reuse 项 done，new 项 pending）。
5. **秒回** `batch_id`，不下载/OCR。**提交无限流**（已移除队列水位/内存/磁盘 429 准入）。

### 1.2 重审/重跑（统一走 worker DB 队列）
| 操作 | 函数 | 行为 |
|------|------|------|
| 重新审核（新建批次） | `submit_recheck_batch` | 新建 recheck 批次，有 ocr_text 写进 `reuse_ocr_text`（worker 跳过下载+OCR 只重跑 LLM）|
| 原地重跑 | `rerun_batch_inplace` | 不新建批次，`requeue_files_for_rerun` 把选中文件重置 pending。`force_all` 无视已有 AI 结果全跑 |
| 批量重判总体 | `start_rejudge_overall` | 只重跑 `judge_batch_overall`（每批 1 次 LLM），不碰单文件、不 OCR |
| 批量重审 | `start_rerun_files_batch` | 逐批 `rerun_batch_inplace`，重跑每个单文件（复用 ocr_text，成本高、串行）|

**`regenerate_criteria` 开关**（重审/批量重审）：为 true 时 `_build_new_criteria_for_batch(ctx)` 按 client_code/client_name/handler/stage 重新生成 criteria 写回 `user_prompt`，让旧批次用上新规则；无业务上下文批次回退 `_fallback_new_criteria()`。

> 老的主进程 fan-out 函数（`_orchestrate_recheck`/`_process_one_recheck`/`_finalize_overall_for_batch`/`_orchestrate_rerun`）已删除，全部统一走 worker DB 队列。

### 1.3 批次总报告 finalize（`_generate_batch_overall` / `_batch_finalize_poll`）
所有文件完成后（主进程轮询 `_batch_finalize_poll`）：
1. 优先 `llm_service.judge_batch_overall`（全部文件明细 + criteria + stage 交 LLM）→ `overall_verdict/score/reason`。
2. LLM 失败回退**规则平均分**：avg≥80→match / ≥50→partial / <50→mismatch + `summarize_batch` 文本兜底。
3. `no_text` 文件从 done_items 排除；全批 no_text → overall=mismatch/0。

### 1.4 watchdog（回收死 worker 任务）
主进程后台协程周期调 `crud.reclaim_expired_leases()`：扫 `status='leased' AND worker_lease_until < now()` 过期行——`retry_count < MAX_RETRY_COUNT(1)` 回 pending + retry+1；否则终态 error。

### 1.5 下载并发
快速检测 fan-out 用 `_DOWNLOAD_SEMAPHORE`（默认 10，env `ARCHIVE_DETECT_DOWNLOAD_CONCURRENCY`）限并发。

## 2. Worker 进程（`worker_runner.py`）

### 2.1 定位
独立进程（`python -m worker_runner --worker-id xxx`），**不是 uvicorn 的一部分**。通过 `SELECT FOR UPDATE SKIP LOCKED` 抢 `archive_detect_files` 的 pending 任务。可多起（生产 systemd 模板 `doc-review-worker@N`）。

### 2.2 主循环
1. 启动：`llm_service.load_config()`、预热 RapidOCR、记 `worker.start` 事件。
2. `claim_one_pending_file()` 抢一个 pending → leased（写 `worker_lease_until = now()+600s`）。
3. `_process_one_file(task, worker_id)`（见 2.3）。
4. 无任务时退避（consecutive_empty 递增 sleep）。
5. SIGTERM/SIGINT → `_should_stop=True`，处理完当前文件优雅退出（TimeoutStopSec=180）。

### 2.3 单文件处理 `_process_one_file`（核心流程）
```text
t0 = now
├─ reuse_ocr_text 非空? ──是──► text = reuse_ocr_text（跳过下载+OCR）
│                        └─否──► 
│      ├─ source_url: update_status(fetching) → fetch_url_to_temp_with_refresh(必要时刷新 URL)
│      │                        校验扩展名
│      ├─ (upload 模式已停用)
│      └─ update_status(ocr) → text_extractor.extract_text → text/page_count/char_count
│              └─ text 为空 → update_file_done(verdict=no_text, status=done) 直接返回（不 error、不重试）
├─ update_status(llm)
├─ get_batch_context(batch_id) → criteria/stage/client_name/handler
├─ llm_service.detect_archival(text, criteria, stage, client_name, handler, batch_id, file_id)  [asyncio.to_thread]
├─ verdict = redactor.redact_dict(verdict)          # 脱敏 reason/key_points
├─ ocr_text_redacted = redactor.redact(text)        # 脱敏 OCR 文本
└─ update_file_done(batch_id, idx, {...verdict 字段..., ocr_text: ocr_text_redacted, elapsed_sec})

异常 ──► update_file_error(batch_id, idx, msg, elapsed, filename) + 记 file.failed 事件
finally ──► 清理临时文件（cleanup_temp_file / upload 本地文件）
```

### 2.4 status 状态机（完整）
见 [03-数据库设计.md §5.3](03-数据库设计.md)。要点：`pending→leased→fetching→ocr→llm→done/error`；`reuse_ocr_text` 走捷径；watchdog 回收超时 leased。

> **.NET 迁移核心**：worker 逻辑（抢任务 + 处理 + 写终态）在 .NET 用后台服务（`IHostedService`/`BackgroundService`）+ Npgsql `SELECT FOR UPDATE SKIP LOCKED` 复刻。OCR/抽取步骤改为**调用 Python OCR 微服务的 HTTP API**。LLM 调用、脱敏、finalize 都在 .NET。

## 3. LLM 服务（`llm_service.py`）

### 3.1 调用封装
- `_get_client()`：进程级共享 OpenAI 客户端（懒加载 + 锁），带超时（connect 10 / read 60 / write 30 / pool 10）。
- `_call_llm(prompt, max_retries=3, *, operation, batch_id, file_id, client_code, task_id)`：调 LLM，429 重试，**每次调用记 `ai_api_calls` 表**（`_log_llm_api` → `insert_ai_api_call_sync`，同步写因跑在 worker 线程）。
- 模型 ID / base_url / api_key 全由 `config.json.llm` 驱动。

### 3.2 各业务 LLM 函数
| 函数 | 用途 | operation |
|------|------|-----------|
| `detect_archival(text, criteria, stage, client_name, handler, ...)` | 留底单文件判定，返回 verdict/match_score/doc_category/reason/key_points | detect_archival |
| `judge_batch_overall(...)` | 批次总体判定，返回 overall_verdict/score/reason | judge_batch_overall |
| `summarize_batch(...)` | 总体文本兜底（LLM 判定失败时） | summarize_batch |
| `detect_and_extract(ocr_texts, ...)` | AI 材料解析：类型检测 + 字段提取 | detect_and_extract |
| `match_bboxes_to_fields(fields, ocr_details)` | 字段与坐标框匹配 | — |
| `classify_one_page` / `detect_page_ranges` | PDF 拆分页分类与页边界判定 | detect_page_ranges |
| `summarize_text(text, progress_name, ...)` | URL 文件摘要 + 相关性判断 | summarize_text |
| `extract_client_profile_facts(ocr_text, filename, doc_category, ...)` | 客户档案事实抽取 | extract_client_profile_facts |
| `detect_large_table_doc(text, ...)` | 大文件 early-exit 初判（OCR 微服务需剥离的依赖） | detect_large_table_doc |

### 3.3 公司售后留底分类体系（硬编码 `ARCHIVE_CATEGORIES_FULL`）
```text
【递交前 5 大类】
A. 客户基础文件（护照/身份证/信息表/简历/出生证明/户口本/毕业证学位证/婚姻文件/房产证/工作证明…）
B. 客户个人文件（职业证书/照片/社保个税/无犯罪/体检/地址证明/资产资信/公证认证/成就类…）
C. 客户公司文件（营业执照/章程/决议/验资/财报审计/银行流水/业务合同/组织架构/股东名册/雇佣合同…）
D. 其他备用文件（律师文件/投资文件/批复留底/使馆申请表/KYC/投资证明/购房文件/入境处表格/商业计划书…）
E. 转款凭证（转账凭证等）
【递交后 4 大类】
F. 文案制作的递交文件类（递交全套留底/补料留底）
G. 获批/失败（通知函/使馆信/批复函/录取通知/补料信/打款通知/体检通知/获身份文件/拒签信/撤案信…）
H. 其他文件（获批后重要证件：更新护照/入境小白条…）
I. 停滞/放弃类文件（撤案/放弃办理的邮件、聊天截图）
```

### 3.4 单文件 prompt 结构（`_build_archive_detect_prompt`）
```
你是公司文件留底审核助手。根据 [公司分类标准] + [用户判定提示词] 审核文件。
---用户判定标准开始---
{user_prompt（criteria）}
---用户判定标准结束---
---公司分类标准开始---
{stage_hint（当前阶段 递交前/递交后）}
{ARCHIVE_CATEGORIES_FULL}
---公司分类标准结束---
重要判定指南:
{client_name/handler 注入}
- 只判断是否与留底分类体系相关，不核对项目名称/投资金额/转账金额
- 姓名匹配客户/办理人/关联人（含拼音英文转写，如「关晓晓」→「GUAN Xiaoxiao」）即强关联
- POA/公证认证文件委托人常为家属/办理人，属有效留底
- 标准证件格式即使 OCR 噪声也判 match/partial
- 服务合同/客户确认聊天/邮件/截图属有效留底证据
- 阶段错配不硬性否决，最多 partial
输出严格 JSON: {verdict, match_score, doc_category, reason, key_points}
```

### 3.5 PSD 业务判定口径（固化在 prompt）
> 留底的本质是**证明该进展对应的服务确已启动或发生**，不是必须有官方回执类关键件。
- 证据 = 官方文件（批复函/受理回执/递交确认）**或** 软证据组合（服务合同 + 聊天/邮件/确认截图）。
- 存在服务启动证据（官方件或软证据任一）→ 整批 **match**；只有辅助附件无服务启动证据 → **partial**；完全无服务痕迹 → **mismatch**。
- 衍生规则：转款凭证以金额币种为准不强制客户姓名；银行开户类核心材料属隐私（账户/开户/转款凭证任一即符合），银行通用材料属正常附带件；阶段错配最多 partial；单份文件失败/加密只影响该文件不拖垮整批。
- 同样固化在总判 prompt `_build_judge_batch_overall_prompt`。

> **.NET 迁移核心**：分类体系 `ARCHIVE_CATEGORIES_FULL`、所有 prompt 模板（单文件 + 总判）、PSD 判定口径都应迁移到 .NET（作为字符串常量 + prompt 拼接函数）。这些是业务知识，与语言无关，直接翻译即可。

## 4. 其他流水线

### 4.1 AI 材料解析
`POST /api/upload` → `_process_file_background`：`ocr_service.process_file`（图片型 PDF 受 max_ocr_pages 限制）→ `detect_and_extract`（类型检测 + 字段提取）→ 内存 `_task_status` 轮询、DB `documents` 存结果 → `PUT /api/result/{task_id}` 人工复核后归档到 clients/family/assets/client_info。

### 4.2 客户档案结构化生成（`client_profile_service.py`）
1. 从客户 `archive_detect_files` 列 done 且有 ocr_text 的文件为候选（`list_source_files` **不带 ocr_text**，生成阶段按 id 重查）。
2. 用户勾选 → 后台 `asyncio.create_task(_generate_background)`。
3. 每文件 `extract_client_profile_facts` 抽取 → **只补空不覆盖**写入 clients/family_members/assets/client_info（`apply_profile_facts`）。

### 4.3 Word 模板（`template_service.py`）
- mammoth HTML 预览、anchor 扫描、marker 注入、docx 渲染。
- docx 预览走 `soffice → PDF → pypdfium2 PNG`；LibreOffice 缺失时降级 HTML。
- 生成：`docx2pdf`（Windows/Word COM，线程内必须 COM 初始化）/ LibreOffice（Linux）。PDF 失败降级 DOCX。

### 4.4 PDF 拆分（`split_service.py` + `split_ocr_service.py`）
`POST /api/split` → `_process_split_background`：`split_extract_all_pages` 全页 OCR（200dpi 单线程）→ `detect_page_ranges` LLM 判页边界 → `normalize_ranges` 规整 → `split_pdf_by_ranges` 拆分。DB `split_tasks` 权威，内存 `_split_task_status` 轮询 fast-path。

### 4.5 URL 摘要
`POST /api/file-summary`（同步）：`fetch_url_to_temp` → `extract_text` → `summarize_text`（摘要 + 相关性 strong/weak/unrelated）→ `summary_crud.create`。

## 5. 可观测性

### 5.1 事件流（`event_service.py`）
`log_event(severity, category, message, context)` fire-and-forget 写 `system_events`。category 常量：`batch.*`/`file.*`/`worker.crash`/`worker.start`/`llm.timeout`/`gc.cleanup`/`db_error` 等。message 截 500 字，context 截 2KB。

### 5.2 外部请求日志（`middleware/request_log_middleware.py`）
**纯 ASGI 中间件**（用 `app.add_middleware` 注册，**不能用 `BaseHTTPMiddleware`**——它读 body 会噎死下游 Pydantic）。只记 `POST /api/archive-detect/business/batch` 的 JSON 请求体到 `api_request_logs`。

### 5.3 调用外部接口记录
URL 刷新等非 AI 出站调用记 `external_api_logs`（service=refresh_url），在 `file_fetcher.refresh_download_url` 埋点（async create_task）。

### 5.4 AI 调用记录
所有 LLM 调用记 `ai_api_calls`，在 `llm_service._call_llm` 埋点（**同步 `insert_ai_api_call_sync`**，因跑在 worker 线程）。prompt/response 原文直存未脱敏，入库前去 NUL/控制字符 + 截断（prompt/response 50KB、error 2KB）。

> 四张日志表（system_events/api_request_logs/external_api_logs/ai_api_calls）都在 `_split_cleanup_loop` 里 GC 30 天。

## 6. 销售线索（`sales_crud.py`）
